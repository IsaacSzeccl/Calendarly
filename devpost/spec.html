Calendarly — how it's built

Next.js on Vercel, Supabase, Google Calendar, GLM (Z.ai), and Brevo. Small enough to demo with six people, built around one rule.

The one rule

Code decides. The model interprets. Plain code works out who is free, which slots exist, the cap of 3 AI-added slots, "only when the organizer is free", and the ranking. The model only reads plain language and writes plain language, and everything it returns must pass a strict format check first. It can be wrong, but it can never break your rules.

A journey through the system

Supabase + Google

Sign-in goes through Supabase and Google. A separate "Connect Google Calendar" step asks for calendar permission; the token is stored encrypted in calendar_connections.

PRD: The Core Journey, step 1. Files: app/page.tsx, app/api/calendar/.

AI job 1 code

The text goes to parsePoll, which returns people, window, hours, and hard/soft constraints. The organizer edits them. On "Create poll", the engine asks Google when the organizer is busy, builds free windows, and saves slots.

PRD: Poll creation in plain language. Files: app/new/page.tsx, lib/ai/parsePoll, lib/engine/slots.

code

The link token finds the poll. On submit the server saves a guest (name, email) and one vote per slot, and sets a private cookie so the guest can return.

PRD: Guest response. Files: app/p/[token]/page.tsx, app/api/guest/.

AI job 2

The statement, today's date, and the guest's timezone go to parseStatement. It returns time ranges and a plain restatement. Nothing is saved as a slot until the guest confirms "What I understood".

PRD: Guest plain-language availability. Files: lib/ai/parseStatement, "What I understood" panel.

code

addAiSlots intersects the ranges with the organizer's free time, removes duplicates, stops at 3, and saves. Earlier voters get the "new options added" email, and the send is logged.

PRD: AI-added slots. Files: lib/engine/addAiSlots, lib/email/.

code AI job 3

The engine ranks the slots and builds the "based on 2 connected calendars, 2 votes, and 1 stated availability" line from counts. explain writes the summary from those numbers. Picking a slot creates the Google event and sends the confirmation email.

PRD: Ranking and AI summary; Finalizing. Files: app/poll/[id]/page.tsx, lib/engine/rank, lib/ai/explain.

The three AI jobs

JobInOut (format-checked)
parsePollOrganizer text, today's date, timezonePeople (and who is required), expected count, window, duration, hours, constraints marked hard or soft, anything not understood
parseStatementGuest text, today's date, guest timezonePlain restatement, time ranges with timezone, a preferences summary, ambiguities
explainRanked slots with counts, constraint results, and conditional alternativesSummary of best and not-best, conditional advice, one explanation per slot

Every call is logged in ai_runs. Invalid output gets one retry, then a plain "I couldn't read that" and nothing is added.

Components and tests

Engine pure code

Slot building on a 30-minute grid (assumption), constraint filtering, per-person status, ranking (yes 1.0, prefer not 0.5, no 0 (assumption)), the AI-slot cap, and the basis text. Fully unit-tested, including Jamie in Europe/London.

Calendar adapter

One interface, three implementations: Google (real), sample (hand-designed demo calendars, labeled), and an in-memory fake for tests.

Poll completion and closing

After each submit, isComplete checks responses against the expected count and emails the organizer "6 of 6 have filled in". Closing is checked on each request, and there is a "Close poll now" button. A scheduled email at the close time needs a timer and is optional.

Meet again stretch, last slice

A "remember me" checkbox (off by default) keeps a guest's calendar connection. "New meeting with this group" copies consenting guests into a new poll and reuses their calendars. Guests can disconnect. If not built, it is narrated as "next", not faked.

Guest identity

Link token finds the poll; an HTTP-only cookie finds the guest. No accounts.

Test suite
  • Unit: the engine.
  • AI evals: golden cases (Tom/Jamie, "Tuesday or Wednesday afternoons, not Mondays"). Mocked by default; LIVE=1 uses the real model.
  • End-to-end: Playwright runs the demo path with a fake calendar and a test-only login.
  • Manual: one real-Google smoke test before recording.
  • CI: GitHub Actions runs it all on every push.

Rankings are recomputed on each dashboard load, never stored. Times are stored in UTC and shown in the viewer's timezone.

Where it can break, and what happens

  • Model output unreadable → one retry, then a rephrase message. Nothing is added.
  • Google token expired or revoked → the person is flagged with a reconnect prompt; ranking continues. In Testing mode I believe refresh tokens expire after 7 days (verify), so reconnect before recording.
  • Model too slow → loading state, time limit, same rephrase path.
  • Email fails → logged and shown to the organizer; the rest carries on.

For your agreement

  • Google-only sign-in (drops email sign-in).
  • Database reachable only from the server; no webhooks or background jobs; dashboard refresh button.
  • Add-to-calendar by link; only the organizer's calendar gets the event.
  • Fonts: Fraunces (headings) and DM Sans (body).
  • Slot grid, default duration, vote weights, and "explicit vote overrides calendar".
  • Poll closing checked on each request; the scheduled close-time email is optional.

What the app is

A calendar-aware group poll. An organizer describes a meeting in plain language; guests answer from a link with no account, can connect Google Calendar, or say when they are free in their own words. An AI note explains the trade-offs, and the organizer picks the time.

The rule that shapes the code: code decides, the model interprets. Free time, candidate slots, the cap on AI-added times, ranking and conditional advice are plain, tested code. The model does three jobs only (read the description, read a guest's statement, write the note), and every answer must pass a schema first.

One action, followed through

A guest connects a calendar and the form fills their answers. This is the path that produced the "everything shows Yes" question during review.

Reference route (3 stops)

This is a reference route to read; it was not walked step by step in a session.

  1. Get the busy times. src/lib/calendar/google.ts, search getBusy and mapFreeBusy. Google's reply becomes a list of {start, end} intervals; titles are never read. A 60-second cache avoids asking Google twice.
  2. Turn them into answers. src/app/p/[token]/page.tsx, search calendarMarks and calendarBusy. A time that overlaps any busy block is pre-filled "no", otherwise "yes"; the guest's own votes always win. busyInside in src/lib/engine/time.ts trims each block to the part inside the time, so the reason can be shown.
  3. Show the reason. src/app/p/[token]/GuestForm.tsx, search on your calendar. The label says "Busy 14:45–16:15 on your calendar" or "Free on your calendar", in the time zone the guest chose with the picker (src/components/ZonePicker.tsx).

A practice to reuse

When the app looks wrong, check the data against its source before changing code.

A reviewer reported that the calendar-filled answers were all "Yes". Rather than adjusting the logic, the free/busy data was compared with Google directly using scripts/diag-busy.ts. The data was right: the calendar being compared was displayed in a different time zone from the poll. The fix was to make the app explain itself (busyInside and the zone picker), pinned by the busyInside tests in tests/unit/slots.test.ts.

On another project, the same approach applies: write a tiny script that prints the raw input and output of the suspicious step, so a "bug" can be told apart from a display problem before any logic changes.

Run it again

Commands

Needs Node 22 and a .env (copy the names from .env.example).

npm install · npm run check:env · npm run dev → http://localhost:3000

npm test runs the unit tests (70 at this snapshot). npm run test:e2e runs the demo path in a browser. E2E_TEST_MODE=1 npm run dev adds a test sign-in and sample calendars; never set it in production.

Deploying

The Vercel project needs the same environment variable names as .env (Supabase, Google, AI, Brevo, APP_URL). Environment variables are not copied from your machine; add them in the Vercel project settings, then redeploy. Add the live address to the Google OAuth redirect URIs and Supabase's redirect URLs.
